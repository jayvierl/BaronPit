# Match discussions on Baron Pit

Review date: November 27, 2026. The public site is [baronpit.com](https://baronpit.com). This branch connects an eligible public game to a voluntary, moderated discussion. The most important product decision is that anyone eligible to post can ask about a game. The post distinguishes its social author from the Riot ID whose game it describes.

## What the product borrows

OP.GG lets players move from a compact result to details about a specific game. Threads gives a post a stable destination, puts the reply close to its parent and offers a path back after sign-in. Here the bridge is **Discuss this match**. A visitor can read the game, choose a champion room, preview a question, follow a contributor and find a reply in Activity. No import or lookup publishes anything. The [reference study](references.md) records desktop/mobile observations, primary links, dates, documentation-only behaviors, cost drivers and acceptance criteria. It includes the limits of the signed-out sessions.

## Data, consent and access

1. **Find the match.** The player route reads the existing bounded Riot snapshot in `wp_players`. Up to 100 rows support detail navigation. The first 20 source rows support social summaries. Social participation uses the email-authenticated `wp_users` ID. `wp_links.verified` is independent of both lookup and ordinary social signup. Only an unambiguous verified association permits the “player verified at posting” label. RSO configuration and approval must be independently demonstrated before granting such a link.
2. **Make a deliberate post.** The composer receives a region, public Riot ID and match ID. The server resolves the tuple, checks visibility and a 24-hour source freshness bound, and derives the public evidence from Riot. It rejects ambiguous, unknown, custom, stale and malformed evidence. The reader sees identity, queue, match patch or missing value, game time, retrieval time, region, result, K/D/A and CS. Without consent the publish call fails. Sign-in carries a safe return path. The writer's draft stays in the browser through the normal sign-in flow.
3. **Store the conversation.** A question or perspective uses the existing `wp_posts`, `wp_decisions`, publication checks and per-account submission intent. The durable attachment is a small named scoreboard with recorded provenance. Rendering projects public fields and recomputes links. The private source identifier supports server-side visibility checks. The post stays at `/post/[id]`; the original game can rotate out of recent history. Expired source links explain that boundary. A repeated submission with the same intent returns one post. A perspective remains in the social feed and its room without entering the unanswered-question or trial queues.
4. **Respond and return.** `wp_comments`, follows, positive reactions, private saves, joined rooms and thread preferences use existing records. Activity derives from visible replies and their visible ancestors. It links to the exact comment. No email or push is added. Filtering precedes ranking. New material appears on refresh. [Feed rules and pagination](feed.md).
5. **Moderate and remove.** Existing probation, rate limits, content screening, account status, room controls, queue and appeal rules apply. A held submission gets a private receipt. Withdrawing a post hides its discussion, activity and saved rendering. Blocks restrict access and interaction in both directions. A mute filters the viewer’s delivery and reads. Removing a verified source owner from a viewer’s accessible identities also suppresses the associated public cards for that viewer. An ordinary unverified claim grants no takedown power over another author. A named participant can report a card for staff review. Account deletion and legal evidence retention follow the existing privacy and safety policies. External copies are out of the platform’s control.
6. **Limit analytics claims.** Aggregate appearances deduplicate by player and match. A sample win rate uses wins divided by the displayed appearances, which can include two different participants in one game. Public queue filtering applies before public aggregation. A fetched scoreboard establishes final inventory, not purchase order or causation. Rank history shows only timestamped observations. A small early sample can support descriptive counts. No “best build,” population percentile or comparison ranking ships here. Before publishing a comparative ranking, agree on cohort, patch, queue, exposure minimum and an uncertainty rule, then verify them against held-out data.

Public analytics and confirmed post attachments share a reviewed queue allowlist. Existing richer internal player records can remain in the bounded cache for private workflows. Anonymous UI, metadata and feed projections must continue to enforce their own access policy. No new database table, migration, background ingestion, external analytics or paid service is introduced.

## Release and rollback

1. Review the isolated fixture proof, screenshots and independent reports linked below. Review and approve any preview database connection independently of production. Git integration deploys a merge to `main`; this branch is for review.
2. Recheck the production alias and Git SHA immediately before a release decision. Rebase and repeat the checks if another change intervened. Run typecheck, lint, all unit/integration tests, production build (including art integrity), built-app smoke and two-browser demo on the candidate. Compare the production-scope Riot/usage/staffing evidence against the operating gates above.
3. Release only with owner approval. Run read-only `npm run check:release -- https://baronpit.com` and verify the deployed SHA, public signed-out paths, art, canonical URLs and absence of test data. Exercise mutating acceptance only on the isolated environment. Monitor auth errors, report queue, Riot 429s, feed latency and database transfer using existing operator dashboards.
4. On a bad release, the existing `SAFETY_PAUSE_PUBLICATION=true` control can pause new participation while protective actions stay available. Use an authorized forward fix or a UI rollback that retains the new public-queue and consent guards. Returning wholesale to the older baseline would reopen those privacy defects. Re-run visibility, withdrawal, reply and notification checks before resuming. No data conversion or destructive rollback is required. Keep existing user posts and moderation records.
